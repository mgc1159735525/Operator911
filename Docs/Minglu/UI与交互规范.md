# UI 与交互规范

好的 UI 让信息容易读，好的交互让行动容易理解、执行和纠正。策略游戏的困难应来自资源取舍、概率和长期后果，而不是寻找按钮、记忆规则或猜测状态。

## 标准与设计技巧

| 标准 | 设计技巧 | 本项目应用 |
| --- | --- | --- |
| 目标和当前位置明确 | 固定导航，显示当前选择；提示附处理入口 | 顶部门槛、选中页签、底部下一步和跳转 |
| 主次分明 | 一屏先看目标，再看选择，最后提交；按空间分组 | 左侧简报、中部事项、右侧方案、底部成员与推进 |
| 行动前可预判 | 成本、收益、失败后果靠近授权按钮 | 骰数、概率、投入、岗位冲突、阶段需求 |
| 状态真实可见 | 区分总量、预留和可用，不能只显示资源总数 | 顶部可用资源、右侧预留预算、夜前汇总 |
| 少记忆、易查找 | 任务筛选、相对期限、就地指南和滚动条 | 待授权/已授权/两夜内截止、今夜截止提示 |
| 反馈可解释 | 显示为什么不可操作，以及可采取的措施 | 招募缺钱/满员原因、不可派遣原因、空城区提示 |
| 可以纠错 | 可逆操作直接做，损失性操作明确列出损失 | 撤回授权、换岗取消、夜前核对 |
| 视觉不成为障碍 | 正文保持对比，颜色附文字，选中/焦点有反馈 | 风险文字、按钮焦点轮廓、可拖动滚动条 |
| 阅读不丢信息 | 长内容滚动，动态计算段落高度 | 所有共用列表、执行报告自适应高度 |
| 操作一致 | 相同概念使用相同名称与入口 | 菜单/指南、Esc 返回、F5 保存、F9 读取 |

颜色语义：暖纸色用于当前选项，朱红按钮用于提交操作，青色用于状态与收益，红色用于风险；必须同时提供文字，不能要求玩家仅靠颜色判断。不要为了统一尺寸把所有文字放大到溢出，也不要为了塞入更多内容无限缩小字体。

逐步呈现：任务卡只回答“是什么、何时到期、目前如何”；右侧回答“谁做、成功概率”；方案弹窗解释完整投入和后果。事件弹窗只用于必须决策或重要状态变化，普通信息留在报告。

## 本轮落地范围

- 共用控件：可拖动滚动条、按钮选中焦点；覆盖首页档案、角色列表、任务、对比、报告、指南等使用共同控件的页面。
- 首脑主界面：可用资源、预留说明、指南与菜单入口；修复 Esc 打开菜单后被清空的错误。
- 任务：四类筛选、相对截止时间、筛选空状态；从地图/经营/下一步定位任务时解除筛选并回到列表顶部。
- 地图：优先定位当地最紧急任务；无待办时留在地图给出说明。
- 人事与链条：显示招募受阻原因，启用/暂停链条立即保存。
- 报告：按文本实际高度排版，避免长记录按固定高度裁切。
- 帮助与设置：游戏中可访问操作指南和声音/显示设置，再返回指挥。
- 夜前审阅：预估收入计入商会联盟收益。

保留已经调整的角色美术与外观比例。本轮不替换图像资源，也不改变骰子与任务的核心规则。

## 验收方法

自动规则检查保护原玩法；按钮流程验证主菜单、指南、筛选、任务授权、链条、事件、存读档；截图检查文字与交互区域。自动检查不能证明“玩家已经觉得好用”。后续真人首次试玩应观察：能否独立完成建链、授权、推进、读报告；是否误解可用资源；是否能解释任务占用链条的代价。记录卡住的位置，再迭代，不用单纯增加说明文字掩盖设计问题。

参考：Nielsen Norman Group [可用性十原则](https://www.nngroup.com/articles/ten-usability-heuristics/) 与 [游戏中的应用](https://www.nngroup.com/articles/usability-heuristics-applied-video-games/)。这些是评估框架，不是自动证明界面质量的评分证书。
